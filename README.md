# Синхронизация CRM → PostgreSQL

Решение [тестового задания Trajectory](https://github.com/TrajectorySPBprod/test-task-backend-2026).
Python 3.9+, Flask, SQLAlchemy, PostgreSQL.

## Что изменено

Раньше почти каждая сущность требовала поиска в JSONB, отдельной записи и commit.
После этого таблица читалась повторно, а очистка делала commit внутри циклов.

Теперь таблица читается один раз. Поиск по CRM id и логину идёт через словари в памяти.
Логин используется, только если он указывает на одну запись `AbstractCustomer`;
несколько сущностей внутри одной записи не делают его неоднозначным.
При смене логина и слиянии индексы в памяти обновляются.
Существующие записи сохраняются через многострочный UPSERT, новые через INSERT,
удаления — через DELETE по id, пакетами по 500 записей. Commit один на весь проход.

Исправлены: обращение к id ещё не сохранённой записи, возврат `None` после слияния,
потеря свежих данных текущей сделки, очистка по имени соседнего элемента,
падение на `name=None`, потеря контактов и компаний.
Общие контакты и компании используют одну актуальную версию по CRM id:
при слиянии старая копия или ссылка только с id не затирает свежие подробности.
Очистка вызывается только после завершения обоих итераторов CRM.
Любая ошибка выходит наружу и откатывает всю транзакцию, включая уже записанные пакеты.
Частичный проход сохраняет прежние исключения статусов `111349` / `143` и не запускает очистку.

## Что оставлено и почему

JSONB и формат `general` / `api_value` сохранены, чтобы не переносить данные в новую схему.
Связь сделок с покупателями остаётся через общую запись `AbstractCustomer`.
Добавлены два GIN-индекса `jsonb_path_ops`: они поддерживают поиск через `@>`
по точным `general.id`, `general.login`, `general.name` внутри массивов.
Это не поиск по подстроке; сам внешний поиск по условию задания не реализован.
См. [документацию PostgreSQL](https://www.postgresql.org/docs/current/datatype-json.html#JSON-INDEXING).

Для простоты сохраняются все оставшиеся записи, без сравнения JSON на изменения.
Весь снимок находится в памяти, поэтому это решение для заданных десятков тысяч сущностей.
Advisory lock не допускает два одновременных запуска синхронизации в одной БД.
Другие процессы во время прохода не должны менять эти JSON-поля: произвольные записи
приложения этот lock не блокирует. Повторяющийся CRM id в разных строках считается ошибкой
данных и прерывает проход, а не выбирается случайная строка.
Стоимость поиска по логину растёт с числом сущностей с этим логином.

## Локальный запуск

Нужны Python 3.9+ и запущенный PostgreSQL. Создайте отдельную базу `crm_sync`.
Команды для Linux/macOS, пароль в примере замените своим:

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
export DATABASE_URL='postgresql+psycopg2://postgres:password@localhost:5432/crm_sync'
python -m flask --app app init-db
python -m flask --app app sync-demo examples/crm.json
```

В PowerShell активация: `.\.venv\Scripts\Activate.ps1`,
переменная: `$env:DATABASE_URL = 'postgresql+psycopg2://postgres:password@localhost:5432/crm_sync'`.
В примере получится две записи: покупатель со сделкой и отдельная сделка без логина.
Повторный запуск обновляет те же записи. Файл считается полной выгрузкой:
отсутствующие сущности удаляются. Для частичного обновления добавьте `--partial`.

Для существующей таблицы `init-db` не добавляет индексы. Примените SQL отдельно, без BEGIN:

```bash
psql -h localhost -U postgres -d crm_sync -f migrations/001_search_indexes.sql
```

Настоящий клиент CRM в исходном репозитории неполный. В `amocrm.py` оставлены простые
модели данных и явная заглушка с `NotImplementedError`, чтобы отсутствие клиента
не выглядело как пустая успешная выгрузка. Для подключения замените `amocrm_get`:
он должен выдавать `Customer` / `Lead`, включая `_embedded`, и выбрасывать ошибку при сбое.
Поля `custom_fields_values` здесь словарь, как в исходном коде, а не сырой ответ amoCRM.
Точка входа сохранена: `collect_leads_customers(is_full=True)` в контексте Flask;
после подключения клиента доступна и команда `python -m flask --app app sync`.

## Проверка

```bash
pip install -r requirements-dev.txt
python -m pytest -q -m 'not postgres'
export TEST_DATABASE_URL="$DATABASE_URL"
python -m pytest -q
```

В PowerShell: `$env:TEST_DATABASE_URL = $env:DATABASE_URL`.
Тесты PostgreSQL создают и удаляют отдельную случайную схему, нужны права на её создание.
Без `TEST_DATABASE_URL` они пропускаются. Проверены сопоставление, неоднозначные логины,
слияния, очистка, частичный режим, повторный запуск, откат при сбоях CRM и записи,
блокировка параллельного запуска и использование GIN через EXPLAIN.
Дополнительно проверено сохранение общих контактов и компаний при слиянии строк.
На Python 3.9.13 и PostgreSQL 17: **36 тестов прошли**.

## Оценка нагрузки: 20 тыс. покупателей + 50 тыс. сделок

Пусть E — сохраняемые существующие строки, N — новые, D — удаляемые.
Число SQL-команд: `2 + ceil(E/500) + ceil(N/500) + ceil(D/500)`.
Две первые команды — advisory lock и чтение таблицы. Инициализация соединения и
BEGIN/COMMIT в формулу не входят. Для 70 тыс. отдельных новых или существующих строк
без удалений это **142 SQL-команды и один commit**; при смешении INSERT/UPSERT — до 143.
При объединении покупателей со сделками строк и пакетов меньше.
На 1001 строке тест подтверждает 5 SQL-команд и один commit для обоих видов записи.
Раньше было не менее 70 тыс. поисков, около 70 тыс. записей и 70 тыс. commit,
не считая поиска по логину и очистки.

Память зависит от размера `api_value` и числа вложенных сущностей. Ориентир на искусственных
2 тыс. покупателей + 5 тыс. сделок без общих логинов: JSON около 3 КБ, 40 дополнительных
полей и один контакт на сущность. На этапе обработки в памяти `tracemalloc` показал
пик около 135.5 МиБ Python-аллокаций. Линейная оценка для 70 тыс. — около 1.32 ГиБ;
с интерпретатором, буферами драйвера и SQL-пакетов стоит закладывать
**1.5–2 ГиБ на процесс**. Если старый снимок и новая выгрузка почти не пересекаются,
они временно хранятся вместе: ориентир **2–3 ГиБ**. Это оценка, а не замер боевого API;
при большем JSON бюджет растёт. Полный прогон на 70 тыс. локально не выполнялся.
